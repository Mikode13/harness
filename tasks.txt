## Step 3 — minimal traceability
- [x] Carry `usage` (tokens) + `duration` in AgentResponse from both engines
      (cost dropped — Codex has no cost field and no free way to price it;
      see comment in models/agent.ts).
- [x] Retry policy for agent calls: `RecoverableError`/`UnrecoverableError`
      (models/errors.ts) classify throws per-agent; `RetryingAgent` wraps
      `Agent` and retries up to 3 attempts unless `UnrecoverableError` or the
      last attempt.
  - [x] KNOWN RISK, resolved: retrying re-runs the WHOLE turn from scratch,
        not just the failed part — a retry could re-run a Codex side effect
        (`command_execution`, `file_change`) that already completed before
        the failure. Resolution: `RecoverableError`/`UnrecoverableError` now
        type `cause` as `string` (models/errors.ts), and on a recoverable
        failure `RetryingAgent` rewrites the retried prompt to include that
        reason ("The past prompt failed for the following reason: ...").
        Verified against the real Codex SDK (ad-hoc script, not committed)
        that a Thread already recalls what happened in a prior turn without
        being told again — server-side session memory persists regardless of
        what the client does with a failed stream. So a retried turn has
        both the injected failure reason and its own session history to
        recognize an action already happened and avoid blindly repeating it.
        This is a mitigation via context, not a structural guarantee (the
        agent could still choose to repeat an action) — accepted as
        sufficient for now; revisit if it proves insufficient in practice.

## Step 4 — first workflow (plan → execute → review) — DONE 2026-08-27
- [x] Plain function, no graph: `OrchestratorAgent` coordinates planner → executor
      → reviewer, each an injected `Agent` (chosen/wired in index.ts, not
      hardcoded to specific engines).
- [x] If review rejects: loop back to plan with the feedback; capped by
      `maxAttempts` (constructor param, validated as a positive integer).
      Deviation from the original plan: the reviewer's decision is a
      Zod-validated structured `{decision: 'approved'|'rejected', feedback}`,
      not free text/'OK' string matching — that was tried first and produced a
      real infinite loop in practice (exact-match never true, no iteration cap).
      A malformed reviewer response retries only the reviewer call (its own
      bounded loop, informed of why the previous response failed), not the
      whole plan/execute cycle.
- [x] Chat and workflow are two consumers of the same Agent contract — confirmed:
      `OrchestratorAgent implements Agent`, `Loop` treats it identically to any
      other agent, no special-casing.
Success (met): a full plan → execute → review cycle runs end to end via
`node src/index.ts`; on failure it eventually recovers or fails cleanly with
`UnrecoverableError`, visible to the user (`Loop` no longer swallows
`RecoverableError` silently either).

## Step 5 — later, all additive
- [x] Live streaming of actions while the agent works — DONE 2026-08-27.
      Not literally "extend Agent with events" as originally sketched: `run()`
      gained a third `callback: (event: ProgressEvent) => void` parameter,
      threaded through `Agent`/`RetryingAgent`/`CodexAgent`/`ClaudeAgent`/
      `OrchestratorAgent`. `ProgressEvent` is a shared, provider-agnostic
      discriminated union (command/search/fileChange/mcpTool/agentMessage/
      reasoning/todoList); each engine maps its own SDK events into it.
      `agent_message` goes to both the callback (live) and `AgentResponse.response`
      (accumulated) — everything else is callback-only, never mixed into the
      final response. Replaces the static loader's post-hoc print entirely.
- [ ] Type-while-thinking (Promise.race between readline question and agent run;
      also restores Ctrl+C during agent calls without pause()).
- [ ] Session persistence (save/resume thread ids). Store `{ name, engine,
      sessionId }` behind a small `SessionStore`-style interface (same pattern
      as `Agent`), so the implementation can change later without touching
      callers. Start with a local JSON file in the user's home dir (same
      pattern the SDKs themselves already use for this — `~/.codex/sessions`,
      `~/.claude/projects/`) — it's runtime user data, not shipped in `dist/`,
      so it never travels with the package. Considered SQLite/an external DB;
      decided against for now — no real multi-user/concurrent-access need
      exists yet to justify it, and it would make the CLI depend on a running
      service instead of "just run node src/index.ts". Revisit only if a
      concrete need for concurrent access or querying appears.
- [ ] Log per-turn usage + duration; consider a run id — once the
      `SessionStore` above exists, write per-turn usage/duration through it
      instead of building a separate persistence mechanism just for this.
      NOT the same as the console.log printed after each turn in
      loopImpl.ts today — that's ephemeral chat output, not persisted, and
      has no run id tying turns together.
